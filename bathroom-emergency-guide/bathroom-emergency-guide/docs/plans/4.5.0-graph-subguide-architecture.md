# Graph-Oriented Subguide Architecture

Status: design specification and implementation backlog
Target: post-4.4 release track, currently named **4.5.0**
Principle: the complete guide remains one graph, while every major region can
also be read and printed as a distinct, self-orienting subguide.

Implementation sequencing and measurable gates are tracked in `docs/plans/4.5.0-roadmap-milestones.md`. The alternate-spec decisions are recorded in `docs/plans/4.4.2-alt-spec-feasibility-and-vega.md`.

## 1. Why this exists

The guide is becoming too long for reliable end-to-end reading. That is not a
reason to remove useful material; it is a reason to expose the structure more
honestly.

A reader should be able to answer three questions within seconds:

1. **Where am I in the bathroom-guide graph?**
2. **What kind of problem does this subguide understand?**
3. **Which neighbouring subguide should I move to when the problem changes?**

The intended object is neither one undifferentiated book nor a folder of
unrelated pamphlets. It is a **family of graph-linked field guides**.

## 2. Core model

Each subguide is a graph region with:

- one stable code;
- one title and short title;
- one colour role;
- one monochrome/pattern role;
- one shape or glyph;
- one set of primary questions;
- explicit incoming and outgoing graph edges;
- a cover, position page, contents page, content pages, and handoff page;
- independent PDF/HTML output as well as inclusion in the master guide.

No meaning may depend on colour alone. Every visual identity is expressed by at
least **code + pattern + shape**, with colour as a fourth redundant channel.

These are candidates, not reserved public codes. A satellite graduates into a
standalone guide only when it has:

- a distinct reader question not already answered well by one core guide;
- enough useful material for roughly 8–20 pages without filler;
- at least two meaningful graph connections;
- its own source-complete end matter;
- at least two visuals that clarify structure, mechanism, evidence, or action;
- no need to repeat a second generic emergency preamble.

Shorter subjects remain inserts, cards, or sections inside a core guide. The
master orientation page shows the core graph first and reveals satellites as a
second layer or index, never as sixteen equally loud entry doors.

## 4. Repeated page grammar

### Cover

Purpose: immediate recognition, not explanation.

Required elements:

- subguide code and title;
- colour field plus clearly visible pattern;
- glyph;
- one-line promise written as subject matter, not project narration;
- optional master-guide title in small type;
- no contents list and no version history paragraph.

Example:

> **B — Alarm and Calm**
> How attention, breath, prediction, overload, and small actions change the
> volume of an anxious state.

### Page 0 — position in the graph

This is a compact technical/orientation page. It is allowed to contain version
metadata because the user explicitly chose this page for that purpose.

Required blocks:

1. **You are here** graph with the current node visually emphasized.
2. Incoming routes: “people usually arrive here from…”
3. Outgoing routes: “move to C when pain/body becomes primary,” etc.
4. Edition metadata:
   - guide version;
   - subguide revision;
   - locale;
   - source review date;
   - standalone/master marker;
   - page count.
5. One compact emergency gate **only in standalone output**. In the master
   guide, the global cover gate is not repeated.
6. Pattern key in words, e.g. “B = horizontal wave pattern.”

This page should feel like a map legend, not an introduction apologizing for
what follows.

### Page 1 — introduction and contents

Required order:

1. a dense, curiosity-first opening model;
2. 4–8 questions the subguide can help investigate;
3. a contents list with page numbers;
4. a “quick experiment” or “first observation” when appropriate;
5. no release history, implementation note, evidence-policy lecture, or generic
   warning wall.

### Content pages

- running header: `CODE / short title / current section`;
- outside-edge tab using code + pattern + glyph;
- footer breadcrumb showing graph position, e.g. `O → B → C`;
- cross-guide links display both destination code and title;
- callouts inherit the subguide identity but keep safety semantics independent;
- emergency red remains reserved for actual urgency and must not be reused as a
  decorative subguide colour without a shape/pattern distinction.

### Final handoff page

- “what changed while reading?”
- better / same / worse / different-problem branch;
- neighbouring graph nodes with one-sentence reasons;
- notes area;
- local contact or preparation fields only when relevant;
- no generic conclusion or congratulatory filler.

## 5. Master-guide versus standalone behaviour

| Element | Master guide | Standalone subguide |
|---|---|---|
| overall cover | once | small family mark only |
| actual-emergency gate | once on master cover | once on subguide page 0 |
| subguide cover | section divider | full cover |
| position page | compact | complete metadata and emergency gate |
| introduction/contents | included | included |
| cross-guide destination | page reference + code | code + title + URL/file hint |
| sources | filtered **Sources and limits** section at the end of each subguide; R holds a deduplicated global index and provenance map | the same filtered source-complete section |
| version history | shared reference only | one-line revision record on page 0 |

This prevents the master guide from repeating the same safety and metadata pages
nine times while keeping detached subguides self-contained. Source-localization
rules and migration are specified in
`docs/plans/subguide-source-localization.md`.

## 6. Pattern system

### Requirements

- recognizable when printed monochrome;
- distinguishable with common colour-vision deficiencies;
- visible at 300 dpi and on the 105 × 297 mm field strip;
- no reliance on subtle lightness differences;
- no moiré-prone microscopic texture;
- no pattern behind body text;
- minimum printed stroke approximately 0.5 pt;
- minimum repeat cell approximately 4 mm in standard A4;
- pattern is used on covers, edge tabs, headers, graph nodes, and small keys—not
  as a full-page reading background.

### Redundant identity

Every occurrence should contain at least two non-colour identifiers:

- visible code (`B`);
- pattern (horizontal waves);
- glyph (wave/breath mark);
- written short title where space permits.

A coloured rectangle without code or pattern is invalid.

### Proposed pattern tokens

```text
O  dots                 • • •
A  concentric rings     ◎
B  horizontal waves     ≋
C  diagonal crosshatch  ╳
D  vertical bars        |||
H  diagonal stripes     ///
Z  staggered brick      ▤
P  node lattice         •—•
R  square grid          #
```

The Unicode examples are mnemonic only. Production patterns should be CSS/SVG
geometry, not font glyphs.

## 7. Data model

Add `src/data/subguides.json` only when implementation begins.

Minimum shape:

```json
{
  "schema": 1,
  "subguides": [
    {
      "id": "B",
      "slug": "alarm-calm",
      "title": "Alarm and Calm",
      "short_title": "Alarm / Calm",
      "chapters": ["03-situations-b-g", "04-calm-guide"],
      "sections": ["B", "E"],
      "colour": "#...",
      "pattern": "horizontal-waves",
      "glyph": "breath-wave",
      "incoming": ["O", "D", "C"],
      "outgoing": ["C", "D", "P"],
      "questions": [],
      "intro": "...",
      "reviewed_on": "YYYY-MM-DD"
    }
  ]
}
```

Validation rules:

- every reader-facing chapter or section has one primary subguide;
- shared sections declare secondary membership explicitly;
- every graph edge is reciprocal or documented as intentionally one-way;
- every pattern ID exists in the pattern registry;
- codes, slugs, colours, glyphs, and titles are unique;
- every subguide has cover, page-0, page-1, and handoff content;
- standalone builds contain only their cited source notes;
- no route points to an absent standalone output.

## 8. Build architecture

### Outputs

```text
build/pdf/guide.pdf
build/pdf/subguides/O-observatory.pdf
build/pdf/subguides/A-responsibility-care.pdf
build/pdf/subguides/B-alarm-calm.pdf
...
build/html/subguides/B-alarm-calm.html
build/qa/subguides/<code>-contact.png
```

Generate all variants in colour and monochrome. Large print can initially remain
master-only; add standalone large print after the base architecture stabilizes.

### Source organisation

Preferred future structure:

```text
src/subguides/<code>/cover.md
src/subguides/<code>/position.md
src/subguides/<code>/intro.md
src/subguides/<code>/handoff.md
src/data/subguides.json
src/patterns/<pattern>.svg
src/style-subguides.css
```

Canonical chapter prose remains in `src/chapters`. Subguide wrappers must not
copy chapter content. Source entries are also generated rather than copied: one
canonical source registry produces the local end-of-subguide **Sources and
limits** blocks and the deduplicated R index.

The visualization pipeline is specified separately in
`docs/plans/visualization-program.md`. Subguide manifests reference reviewed
figure IDs rather than embedding one-off image paths.

### CSS strategy

Wrap each region:

```html
<section class="subguide" data-subguide="B" data-pattern="horizontal-waves">
```

Provide tokens:

```css
--subguide-colour
--subguide-colour-soft
--subguide-pattern-image
--subguide-glyph
```

Use the pattern in pseudo-elements, edge tabs, page furniture, and graph nodes.
Keep text surfaces plain.

## 9. Graph rules

The graph should answer routing questions, not display every chapter heading.

- Nodes are subguides.
- Edges are meaningful transitions.
- Edge labels state the trigger: “pain becomes primary,” “unsafe place,”
  “environmental source,” “needs professional destination.”
- The current node is emphasized by code, heavy outline, pattern, and label.
- Neighbouring nodes remain readable in monochrome.
- The full graph appears on each page 0; a local neighbourhood graph may appear
  in running navigation.
- Graph text has a complete list fallback.
- The graph never becomes the only route.

## 10. Editorial contract for every subguide

1. Begin with a model, observation, experiment, or surprising fact.
2. Avoid “this chapter explains…” and release/project narration.
3. Keep the actual-emergency gate singular within each independently printable
   object.
4. Separate sensation, interpretation, action, and escalation.
5. Give uncertainty something useful to do.
6. Keep humour near explanation, away from the action gap in immediate danger.
7. End sections with a next observation or graph transition, not a summary of
   what the section just said.
8. Prefer tables only when comparison is genuinely faster than prose.
9. Every source number keeps scope and limit nearby.
10. A reader may enter at any subguide without reading O first.

## 12. Questions to resolve at prototype review

1. Should B/E and Calm remain one subguide or become two?
2. Should pain and first aid share C, or should first aid be a detachable insert?
3. Should Situation G sit with threat D or professional support P?
4. Is R printed by default, or offered as a separate reference pack?
5. Should pattern appear on the outside edge only, or also in running headers?
6. Does the field-strip edition need abbreviated covers to avoid wasting one
   narrow page per subguide?
7. Should the master guide use full subguide covers or compact divider spreads?
8. Which satellite modules deserve promotion first: Small-Room Physics,
   Decision Science, Sanitation/Plumbing, or Human Factors/Handoffs?
9. Should local Sources and limits use full entries in the master, or concise
   entries with the full canonical details in the R index?
10. Which visual families need to be present before the first standalone
    subguide release: graph, mechanism, quantitative evidence, and handoff?

The first prototype should answer these visually before the architecture becomes
expensive.
